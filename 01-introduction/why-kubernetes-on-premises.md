# 왜 온프레미스에서 Kubernetes인가?

> "온프레미스에서 VM 잘 쓰고 있는데, 왜 굳이 Kubernetes를 도입해야 하나요?"

정당한 질문입니다. Kubernetes는 복잡합니다. 학습 곡선도 가파릅니다. 그런데도 많은 기업들이 온프레미스에 Kubernetes를 도입하는 이유가 있습니다.

## VM vs Container: 무엇이 다른가

먼저 기본적인 차이부터 이해해 봅시다.

### Virtual Machine (VM) 방식

```
┌─────────────────────────────────────────┐
│           Application A                 │
├─────────────────────────────────────────┤
│     Guest OS (Ubuntu 20.04)             │
├─────────────────────────────────────────┤
│           Hypervisor                    │
├─────────────────────────────────────────┤
│     Host OS (Linux/Windows)             │
├─────────────────────────────────────────┤
│           Hardware                      │
└─────────────────────────────────────────┘
```

- 각 VM마다 완전한 OS를 실행
- 부팅에 몇 분 소요
- GB 단위의 디스크 사용
- 안정적이고 검증된 기술

### Container 방식

```
┌──────────┐ ┌──────────┐ ┌──────────┐
│  App A   │ │  App B   │ │  App C   │
├──────────┤ ├──────────┤ ├──────────┤
│Container │ │Container │ │Container │
├──────────┴─┴──────────┴─┴──────────┤
│        Container Runtime            │
├─────────────────────────────────────┤
│          Host OS (Linux)            │
├─────────────────────────────────────┤
│            Hardware                 │
└─────────────────────────────────────┘
```

- 호스트 OS 커널 공유
- 시작에 몇 초 소요
- MB 단위의 이미지
- 더 효율적인 리소스 사용

### 비교 요약

| 측면 | VM | Container |
|------|-----|-----------|
| 시작 시간 | 분 | 초 |
| 리소스 오버헤드 | 높음 | 낮음 |
| 격리 수준 | 강함 | 중간 |
| 이미지 크기 | GB | MB |
| 이식성 | 하이퍼바이저 의존 | 어디서나 동일 |

## 그렇다면 왜 Kubernetes?

Container만으로는 충분하지 않습니다. Container가 1-2개일 때는 `docker run`으로 충분합니다. 하지만 수십, 수백 개의 Container를 운영해야 한다면?

### 문제 상황

```
"App A의 Container가 죽었어요"
    → 누가 다시 시작하지?

"트래픽이 급증했어요"
    → 누가 Container를 더 띄우지?

"새 버전을 배포해야 해요"
    → 어떻게 다운타임 없이?

"App A는 App B와 통신해야 해요"
    → IP가 계속 바뀌는데?
```

이 모든 것을 수동으로 관리하는 것은 불가능합니다.

### Kubernetes의 답

Kubernetes는 이 문제들을 **선언적(Declarative)**으로 해결합니다.

```yaml
# "이 상태를 유지해주세요"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3                    # 항상 3개 유지해주세요
  selector:
    matchLabels:
      app: my-app
  template:
    spec:
      containers:
      - name: my-app
        image: my-app:v1.2.3
        resources:
          requests:
            memory: "128Mi"      # 최소 128MB 메모리
            cpu: "100m"          # 최소 0.1 CPU
```

이 YAML을 적용하면 Kubernetes가:

1. ✅ Container 3개를 자동 생성
2. ✅ 하나가 죽으면 자동 재시작
3. ✅ 노드가 죽으면 다른 노드에서 재생성
4. ✅ 롤링 업데이트로 무중단 배포

## 온프레미스 + Kubernetes의 시너지

### 1. 기존 인프라 활용

```
                        ┌─────────────────┐
   기존 투자            │  Bare Metal     │
   ─────────►          │  Servers        │
                       │  (감가상각 중)   │
                        └───────┬─────────┘
                                │
                                ▼
                        ┌─────────────────┐
   Kubernetes로         │  K8s Worker     │
   ─────────►          │  Nodes          │
                        └───────┬─────────┘
                                │
                                ▼
                        ┌─────────────────┐
   현대적 운영          │  Container      │
   ─────────►          │  Workloads      │
                        └─────────────────┘
```

5년 전에 구매한 서버들을 Kubernetes Worker Node로 전환하면, 기존 투자를 보호하면서도 현대적인 운영 방식을 적용할 수 있습니다.

### 2. 클라우드와 동일한 경험

온프레미스에서 Kubernetes를 운영하면:

```yaml
# 이 YAML은 어디서든 동일하게 동작
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
...
```

- 개발팀은 한 가지 방식만 학습
- CI/CD 파이프라인 통일
- 클라우드 ↔ 온프레미스 간 애플리케이션 이동 용이

### 3. 자동화된 운영

기존 VM 기반 운영:

```
새벽 2시 알람: "서버 죽음"
    ↓
운영자 깨어남
    ↓
VPN 접속
    ↓
SSH로 서버 확인
    ↓
서비스 수동 재시작
    ↓
다시 잠
```

Kubernetes 기반 운영:

```
새벽 2시: Pod 죽음
    ↓
Kubernetes: "3개 유지해야 하는데 2개네?"
    ↓
자동으로 새 Pod 생성
    ↓
운영자: 😴 (계속 수면)
    ↓
아침에 로그 확인: "아 어젯밤에 Pod 하나 재시작됐네"
```

## 그래서 EKS를 온프레미스에서?

Kubernetes를 직접 구축하고 운영하는 것은 어렵습니다. 정말 어렵습니다.

> ⚠️ **주의**
>
> **직접 구축 시 고려사항**
>
> - etcd 클러스터 고가용성 구성
> - Control Plane 이중화
> - 인증서 관리 및 갱신
> - 업그레이드 계획 및 실행
> - 네트워크 플러그인 선택 및 관리
> - 스토리지 프로비저너 구성
> - 모니터링/로깅 스택 구축
> - 보안 패치 및 CVE 대응
> - ...그리고 더 많은 것들

이 모든 것을 직접 하지 않아도 됩니다. AWS는 두 가지 방법을 제공합니다:

| 방식 | 특징 |
|------|------|
| **EKS Hybrid Nodes** | Control Plane은 AWS가 관리, 온프레미스 서버를 Worker Node로 연결 |
| **EKS Anywhere** | 전체 클러스터를 온프레미스에서 운영, AWS의 도구와 지원 활용 |

다음 장에서는 Kubernetes의 기본 개념을 더 자세히 알아보고, 그 다음에 이 두 솔루션을 비교해 보겠습니다.
