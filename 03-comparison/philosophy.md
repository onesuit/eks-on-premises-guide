# 철학적 차이

> "같은 회사에서 왜 비슷한 제품을 두 개나 만들었을까요?"

EKS Hybrid Nodes와 EKS Anywhere는 **다른 문제를 해결하기 위해** 만들어졌습니다. 이 철학적 차이를 이해하면 선택이 쉬워집니다.

## 두 솔루션이 탄생한 배경

### 2021년: EKS Anywhere의 등장

2021년, 많은 기업들이 이런 고민을 했습니다:

```
"Kubernetes 좋은 건 알겠는데..."

❓ 우리 데이터센터에서 직접 운영해야 하는데, 어떻게 하지?
❓ VMware 환경에서 K8s를 어떻게 돌리지?
❓ 인터넷 연결이 안 되는 곳에서도 K8s가 필요한데?
❓ 직접 구축하자니 너무 복잡하고, 매니지드 서비스는 클라우드에만 있고...
```

AWS의 답: **EKS Anywhere**

> "EKS의 도구와 경험을 온프레미스에서도 쓸 수 있게 해드릴게요. Control Plane도 직접 운영하세요."

### 2024년: EKS Hybrid Nodes의 등장

시간이 지나면서 다른 요구가 나타났습니다:

```
"AWS EKS 잘 쓰고 있는데..."

❓ 일부 워크로드는 온프레미스에서 돌려야 하는데?
❓ 데이터는 온프레미스에 두고, 관리는 AWS에서 하고 싶은데?
❓ Control Plane 관리하기 싫은데, Worker만 온프레미스에 두면 안 되나?
❓ AWS 서비스랑 연동하면서 온프레미스도 쓰고 싶은데?
```

AWS의 답: **EKS Hybrid Nodes**

> "EKS Control Plane은 우리가 관리할게요. 여러분 서버를 Worker Node로 연결만 하세요."

## 근본적인 철학 차이

### EKS Hybrid Nodes: "클라우드 확장"

```
철학: AWS 클라우드를 온프레미스로 확장한다

핵심 가정:
├── AWS 클라우드가 중심이다
├── 온프레미스는 클라우드의 연장선이다
├── 안정적인 네트워크 연결이 있다
└── AWS 서비스 통합이 중요하다

                    중심
                     │
              ┌──────┴──────┐
              │  AWS Cloud  │
              │             │
              │  EKS        │
              │  Control    │
              │  Plane      │
              └──────┬──────┘
                     │
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
   ┌─────────┐ ┌─────────┐ ┌─────────┐
   │ Cloud   │ │ Cloud   │ │On-Prem  │
   │ Worker  │ │ Worker  │ │ Worker  │
   │ (EC2)   │ │ (EC2)   │ │(Hybrid) │
   └─────────┘ └─────────┘ └─────────┘
```

### EKS Anywhere: "온프레미스 독립"

```
철학: 온프레미스에서 독립적으로 운영한다

핵심 가정:
├── 온프레미스가 중심이다
├── 클라우드 연결은 선택사항이다
├── 완전한 통제권이 필요하다
└── Air-gapped 환경도 지원해야 한다

                    중심
                     │
        ┌────────────┴────────────┐
        │      On-Premises        │
        │                         │
        │  ┌───────────────────┐  │
        │  │  EKS Anywhere     │  │
        │  │  Control Plane    │  │
        │  └─────────┬─────────┘  │
        │            │            │
        │  ┌─────────┴─────────┐  │
        │  │   Worker Nodes    │  │
        │  └───────────────────┘  │
        │                         │
        └────────────┬────────────┘
                     │
                  (선택적)
                     │
                     ▼
              ┌──────────────┐
              │  AWS Cloud   │
              │  (콘솔 연동) │
              └──────────────┘
```

## 운영 철학의 차이

### 책임 분담 모델

| 영역 | EKS Hybrid Nodes | EKS Anywhere |
|------|------------------|--------------|
| **etcd 관리** | AWS | 고객 |
| **API Server 관리** | AWS | 고객 |
| **Control Plane 업그레이드** | AWS (버튼 클릭) | 고객 (eksctl anywhere) |
| **Control Plane 모니터링** | CloudWatch | 고객 구성 |
| **인증서 갱신** | AWS 자동 | 고객 관리 |
| **Worker Node 관리** | 고객 | 고객 |
| **네트워크 구성** | 고객 | 고객 |
| **스토리지 구성** | 고객 | 고객 |

### 장애 시나리오별 대응

**시나리오 1: Control Plane 장애**

```
EKS Hybrid Nodes:
├── AWS SLA 적용 (99.95%)
├── AWS가 자동 복구
└── 고객: "티켓 넣고 기다림"

EKS Anywhere:
├── 고객이 직접 복구
├── 백업에서 etcd 복원
└── 고객: "새벽에 콜 받으면 직접 대응"
```

**시나리오 2: 네트워크 단절**

```
EKS Hybrid Nodes:
├── 기존 Pod는 계속 실행
├── 새 Pod 배포 불가
├── kubectl 명령 불가
└── 연결 복구 필요

EKS Anywhere:
├── 완전히 정상 운영
├── 새 Pod 배포 가능
├── kubectl 정상 동작
└── 영향 없음
```

## AWS의 하이브리드 전략

AWS는 "모든 것을 클라우드로"에서 "적절한 곳에서 실행"으로 전략이 변화했습니다:

```
2015-2020: "모든 것을 AWS로 가져오세요"
                │
                ▼
2020-현재: "어디서 실행하든 AWS 경험을 제공합니다"
                │
                ├── AWS Outposts (AWS 하드웨어를 고객 데이터센터에)
                ├── EKS Anywhere (K8s를 어디서든)
                ├── EKS Hybrid Nodes (EKS를 온프레미스로 확장)
                └── Local Zones, Wavelength (엣지로 확장)
```

이 전략 변화의 이유:

1. **현실 인정**: 모든 워크로드가 퍼블릭 클라우드로 갈 수 없다
2. **고객 요구**: 하이브리드 환경 지원 요청 증가
3. **경쟁**: Azure Arc, Google Anthos와의 경쟁
4. **시장 확장**: 온프레미스 고객도 AWS 생태계로

## 어떤 철학이 우리에게 맞을까?

### "클라우드 확장" 철학이 맞는 조직

```
✅ 이미 AWS를 주력으로 사용 중
✅ "관리형"을 선호 (SaaS, PaaS, Managed Services)
✅ 운영팀 규모가 작음
✅ 클라우드 네이티브 문화
✅ 24/7 온콜 부담을 줄이고 싶음
```

### "온프레미스 독립" 철학이 맞는 조직

```
✅ 온프레미스가 주력, 클라우드는 보조
✅ 인프라 완전 통제권 필요
✅ 규정상 외부 연결 제한
✅ 충분한 운영 역량 보유
✅ 특수 환경 (공장, 선박, 군사 시설 등)
```
