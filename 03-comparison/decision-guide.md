# 선택 가이드

> "비교는 알겠는데, 결국 우리는 뭘 선택해야 하나요?"

이 페이지에서는 다양한 시나리오별로 어떤 솔루션이 적합한지 안내합니다.

## 시나리오별 추천

### 시나리오 1: AWS 중심 하이브리드

**상황**:
- 현재 AWS EKS 사용 중
- 일부 워크로드만 온프레미스 필요
- AWS 서비스(RDS, S3, Lambda 등) 적극 활용

**추천**: ✅ **EKS Hybrid Nodes**

```
이유:
├── 기존 EKS 클러스터에 노드만 추가
├── IAM, CloudWatch 등 기존 설정 그대로 사용
├── Pod Identity로 AWS 서비스 접근 용이
└── 운영팀 학습 곡선 최소화
```

### 시나리오 2: 규제 산업 (금융/의료)

**상황**:
- 데이터가 반드시 온프레미스에 있어야 함
- 감사 및 규정 준수 중요
- 인터넷 연결은 있지만 제한적

**추천**: 🤔 **둘 다 가능, 요구사항에 따라**

```
규정이 "데이터만 온프레미스"라면:
└── EKS Hybrid Nodes ✅
    (Control Plane 메타데이터는 AWS에 저장됨)

규정이 "모든 것이 온프레미스"라면:
└── EKS Anywhere ✅
    (전체 인프라를 직접 통제)
```

> ⚠️ **주의**
>
> **규제 환경에서 주의할 점**
>
> EKS Hybrid Nodes는 Pod 메타데이터, 노드 정보 등이 AWS Control Plane에 저장됩니다. 규정이 이를 허용하는지 법무팀/컴플라이언스팀과 확인하세요.

### 시나리오 3: 완전 오프라인 환경

**상황**:
- 인터넷 연결 없음 (공장, 선박, 군사 시설)
- Air-gapped 환경
- 물리적으로 격리된 네트워크

**추천**: ✅ **EKS Anywhere (유일한 선택)**

```
EKS Anywhere Disconnected 모드:
├── 컨테이너 이미지를 로컬 레지스트리에 미러링
├── 모든 의존성을 로컬에 준비
├── 인터넷 없이 완전 독립 운영
└── 업그레이드도 오프라인 가능
```

### 시나리오 4: VMware vSphere 환경

**상황**:
- 기존 VMware 인프라 보유
- vCenter로 VM 관리 중
- K8s를 VM 위에서 운영 예정

**추천**: ✅ **EKS Anywhere**

```
EKS Anywhere on vSphere:
├── vSphere 네이티브 통합
├── VM 템플릿 기반 노드 프로비저닝
├── vCenter에서 리소스 관리
├── 기존 vSphere 운영 방식 유지
└── CAPV (Cluster API Provider vSphere) 사용
```

> 💡 **참고**
>
> **참고**: EKS Hybrid Nodes는 vSphere를 직접 지원하지 않습니다. vSphere VM을 베어메탈처럼 수동 구성해야 합니다.

### 시나리오 5: 엣지 컴퓨팅

**상황**:
- 매장, 공장, 창고 등 분산된 위치
- 각 위치에 소규모 클러스터 필요
- 중앙에서 관리하고 싶음

**추천**: 🤔 **규모와 연결성에 따라**

```
연결 안정적 + 소수 노드:
└── EKS Hybrid Nodes ✅
    중앙 EKS에서 여러 위치의 노드 관리

연결 불안정 또는 완전 독립:
└── EKS Anywhere ✅
    각 위치별 독립 클러스터
    EKS Connector로 중앙 가시성
```

### 시나리오 6: 비용 최적화가 최우선

**상황**:
- 예산이 매우 제한적
- 가능한 모든 비용 절감 필요
- 운영 인력은 있음

**추천**: ✅ **EKS Anywhere**

```
비용 비교 (노드 10개, 4 vCPU 기준):

EKS Hybrid Nodes:
├── EKS Control Plane: $73/월
├── Hybrid Node: 10 × 4 × $0.01 × 730시간 = $292/월
└── 총: ~$365/월

EKS Anywhere:
├── 소프트웨어 비용: $0
├── (선택) Enterprise Support: 별도
└── 총: 하드웨어/인프라 비용만
```

### 시나리오 7: 운영 간소화가 최우선

**상황**:
- 작은 운영팀
- K8s 전문가 부족
- 관리 부담 최소화 희망

**추천**: ✅ **EKS Hybrid Nodes**

```
운영 부담 비교:

EKS Hybrid Nodes:
├── etcd: AWS 관리 ✅
├── Control Plane 업그레이드: 버튼 클릭 ✅
├── 인증서 갱신: 자동 ✅
├── 장애 대응: AWS Support ✅
└── 야간 콜아웃: Control Plane 관련 없음 ✅

EKS Anywhere:
├── etcd: 직접 관리 및 백업
├── Control Plane 업그레이드: 직접 수행
├── 인증서 갱신: 직접 관리
├── 장애 대응: 직접 대응
└── 야간 콜아웃: 가능성 있음
```

## 결정 매트릭스

각 항목에 점수를 매겨보세요 (1-5점):

| 질문 | 점수 | Hybrid Nodes | Anywhere |
|------|------|:------------:|:--------:|
| AWS 서비스 통합이 중요하다 | ___ | +점수 | - |
| 인터넷이 항상 안정적이다 | ___ | +점수 | - |
| Control Plane 관리하고 싶지 않다 | ___ | +점수 | - |
| VMware vSphere를 사용한다 | ___ | - | +점수 |
| 완전 오프라인 운영이 필요하다 | ___ | - | +점수 |
| 비용 절감이 최우선이다 | ___ | - | +점수 |
| 완전한 통제권이 필요하다 | ___ | - | +점수 |

**결과**:
- Hybrid Nodes 점수 > Anywhere 점수 → EKS Hybrid Nodes 추천
- Anywhere 점수 > Hybrid Nodes 점수 → EKS Anywhere 추천
- 비슷하다면 → 운영 역량과 조직 문화 고려

## 마이그레이션 경로

### 기존 EKS → Hybrid Nodes

```
상대적으로 쉬움

1. 온프레미스 네트워크 연결 (VPN/DX)
2. 온프레미스 서버 준비 (OS, containerd)
3. SSM Agent 설치 및 노드 등록
4. 워크로드 점진적 이동 (node affinity 활용)
```

### 기존 EKS → Anywhere

```
새로운 클러스터 구축 필요

1. EKS Anywhere 클러스터 새로 생성
2. 워크로드 YAML/Helm 차트 마이그레이션
3. GitOps 파이프라인 재구성
4. 기존 클러스터와 병행 운영 후 전환
```

### 기존 K8s (vanilla/RKE/etc) → 둘 중 하나

```
새로운 클러스터 구축 필요 (둘 다)

EKS 생태계 도입 시:
├── EKS Add-ons 활용 가능
├── eksctl 기반 관리
├── AWS 통합 이점
└── 기존 YAML 대부분 호환
```

## 최종 추천

> ✅ **완료**
>
> **EKS Hybrid Nodes를 선택하세요** if:
> - AWS가 주력이고 온프레미스는 보조
> - 운영 부담을 줄이고 싶음
> - 안정적인 네트워크 연결 가능

> ✅ **완료**
>
> **EKS Anywhere를 선택하세요** if:
> - 온프레미스가 주력
> - 완전한 독립 운영 필요
> - VMware 환경이거나 Air-gapped
