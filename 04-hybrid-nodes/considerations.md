# 주의사항과 제약

> "좋은 건 알겠는데, 단점은 없나요?"

모든 기술에는 트레이드오프가 있습니다. EKS Hybrid Nodes를 도입하기 전에 알아야 할 제약사항과 주의점을 살펴봅시다.

## 핵심 제약사항

### 1. AWS 연결 필수

가장 중요한 제약입니다. **인터넷(또는 전용 연결)이 끊기면 새로운 작업이 불가능합니다.**

```
AWS 연결 상태에 따른 기능:

연결 정상:
├── ✅ 새 Pod 배포
├── ✅ kubectl 명령
├── ✅ 스케일링
├── ✅ 모니터링
└── ✅ 모든 기능 정상

연결 끊김:
├── ✅ 기존 Pod 계속 실행
├── ✅ 기존 Service 정상 동작
├── ❌ 새 Pod 배포 불가
├── ❌ kubectl 명령 불가
├── ❌ 스케일링 불가
├── ❌ Pod 재시작 시 이미지 Pull 실패 가능
└── ❌ 모니터링 데이터 누락
```

> ⚠️ **주의**
>
> **연결 끊김 시나리오 대비**
>
> * 네트워크 이중화 (VPN + Direct Connect)
> * 필수 이미지 로컬 캐싱
> * 긴급 상황용 런북 준비

### 2. 네트워크 레이턴시

Control Plane이 클라우드에 있으므로 레이턴시가 발생합니다.

```
┌────────────────────────────────────────────────────────────────────┐
│                                                                    │
│   kubectl apply                                                    │
│        │                                                           │
│        │  ① API 요청 (클라우드로)                                 │
│        ▼  ~20-50ms (VPN/인터넷)                                   │
│   ┌─────────────┐                                                  │
│   │ API Server  │  ② 처리                                         │
│   │ (AWS)       │  ~10ms                                           │
│   └──────┬──────┘                                                  │
│          │  ③ kubelet에 지시                                      │
│          │  ~20-50ms                                               │
│          ▼                                                         │
│   ┌─────────────┐                                                  │
│   │   kubelet   │  ④ 컨테이너 생성                                │
│   │ (On-Prem)   │                                                  │
│   └─────────────┘                                                  │
│                                                                    │
│   총 레이턴시: ~100-150ms (vs 클라우드 ~30ms)                     │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

**영향받는 작업:**

| 작업         | 영향    |
| ---------- | ----- |
| Pod 생성     | 약간 느림 |
| kubectl 응답 | 체감됨   |
| HPA 반응     | 지연 가능 |
| 대량 배포      | 시간 증가 |

**영향받지 않는 작업:**

| 작업         | 이유                |
| ---------- | ----------------- |
| Pod 간 통신   | 로컬 네트워크 사용        |
| Service 접근 | kube-proxy가 로컬 처리 |
| 컨테이너 실행    | kubelet이 로컬 처리    |

### 3. 비용 구조

vCPU 기반 과금이 추가됩니다.

```
EKS Hybrid Nodes 비용 계산:

기본 EKS 비용:
└── $0.10/시간 (Control Plane)
    = $73/월

Hybrid Node 추가 비용:
└── vCPU당 $0.01/시간

예시: 10대 서버 × 4 vCPU
└── 10 × 4 × $0.01 × 730시간 = $292/월

총 비용 = $73 + $292 = $365/월
```

**비용 비교표:**

| 규모        | EKS Hybrid Nodes | EKS Anywhere | 직접 운영 |
| --------- | ---------------- | ------------ | ----- |
| 10 vCPU   | \~$100/월         | $0           | 인건비   |
| 100 vCPU  | \~$800/월         | $0           | 인건비   |
| 500 vCPU  | \~$3,700/월       | 지원 구독        | 인건비   |
| 1000 vCPU | \~$7,400/월       | 지원 구독        | 인건비   |

> 💡 **참고**
>
> **비용 최적화 팁**
>
> * 실제 필요한 vCPU만 노드에 할당
> * 사용하지 않는 노드는 클러스터에서 제거
> * ARM 기반 서버 활용 검토

### 4. 네트워크 구성 복잡성

Pod CIDR과 VPC CIDR이 겹치면 안 됩니다.

```
❌ 잘못된 구성:
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   AWS VPC: 10.0.0.0/16                                         │
│                                                                 │
│   On-Premises Network: 10.0.0.0/8  ← 겹침!                     │
│   Pod CIDR: 10.244.0.0/16  ← VPC와 충돌 가능                   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

✅ 올바른 구성:
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   AWS VPC: 10.0.0.0/16                                         │
│                                                                 │
│   On-Premises Network: 192.168.0.0/16  ← 겹치지 않음          │
│   Pod CIDR: 100.64.0.0/16  ← 별도 대역                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 5. 지원 OS 제한

모든 리눅스 배포판을 지원하지 않습니다.

```
지원 OS:
├── ✅ Amazon Linux 2023
├── ✅ Bottlerocket (vSphere만)
├── ✅ Ubuntu 20.04, 22.04
├── ✅ RHEL 8, 9
└── ❌ CentOS, Debian, SUSE 등은 미지원

주의:
└── 기존에 CentOS를 사용 중이라면 OS 마이그레이션 필요
```

## 운영 시 주의사항

### 네트워크 모니터링

AWS 연결 상태를 항상 모니터링해야 합니다.

```yaml
# AWS 연결 상태 체크 Pod 예시
apiVersion: v1
kind: Pod
metadata:
  name: aws-connectivity-checker
  namespace: monitoring
spec:
  nodeSelector:
    eks.amazonaws.com/compute-type: hybrid
  containers:
  - name: checker
    image: curlimages/curl
    command:
    - /bin/sh
    - -c
    - |
      while true; do
        if curl -s --max-time 5 https://eks.ap-northeast-2.amazonaws.com > /dev/null; then
          echo "$(date): AWS connectivity OK"
        else
          echo "$(date): AWS connectivity FAILED"
          # 알림 전송 로직
        fi
        sleep 30
      done
```

### 이미지 레지스트리 전략

네트워크 문제에 대비한 이미지 전략:

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  Primary: ECR (AWS)                                            │
│  └── 정상 시 사용                                              │
│                                                                 │
│  Fallback: 온프레미스 레지스트리 (Harbor, etc.)                │
│  └── 네트워크 장애 시 사용                                     │
│                                                                 │
│  전략:                                                          │
│  1. 중요 이미지는 온프레미스에도 미러링                        │
│  2. imagePullPolicy: IfNotPresent 사용                         │
│  3. 노드에 이미지 프리페칭                                     │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 업그레이드 계획

Hybrid Node 업그레이드 순서:

```
1. Control Plane 업그레이드 (AWS 콘솔)
   └── AWS가 자동으로 수행, 몇 분 소요

2. Cloud Worker Node 업그레이드
   └── 새 노드 그룹 또는 in-place

3. Hybrid Node 업그레이드  ← 여기서 주의!
   └── 직접 수행 필요
   
   절차:
   a. 노드 drain
      kubectl drain hybrid-node-001 --ignore-daemonsets
   
   b. nodeadm 업그레이드
      sudo nodeadm upgrade
   
   c. 노드 uncordon
      kubectl uncordon hybrid-node-001
```

> ⚠️ **주의**
>
> **업그레이드 주의사항**
>
> * Control Plane과 Node 버전 차이는 최대 2 마이너 버전
> * 업그레이드 전 백업 필수
> * 한 번에 하나씩, 순차적으로

## 적합하지 않은 경우

| 상황                          | 이유                       | 대안                      |
| --------------------------- | ------------------------ | ----------------------- |
| Air-gapped 환경               | AWS 연결 불가                | EKS Anywhere            |
| 불안정한 네트워크                   | 연결 끊김 시 제약               | EKS Anywhere            |
| 1000+ vCPU 대규모              | 비용 부담                    | EKS Anywhere + 지원       |
| VMware vSphere 네이티브 통합이 필요함 | Hybrid Nodes는 인프라 통합이 없음 | EKS Anywhere on vSphere |
| 완전한 통제권 필요                  | Control Plane 접근 불가      | EKS Anywhere            |
