# 왜 여러 클러스터가 필요한가

> "하나의 클러스터로 다 해결할 수 없나요?"

이론적으로는 가능합니다. 하지만 실제 운영에서는 여러 클러스터가 더 안전하고 효율적인 경우가 많습니다.

## 단일 클러스터의 한계

### 1. 장애 영향 범위

```
단일 클러스터:
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   Control Plane 장애 발생!                                     │
│   ════════════════════════                                     │
│                    │                                            │
│                    ▼                                            │
│   ┌──────────────────────────────────────────────────────────┐ │
│   │              모든 환경 영향                               │ │
│   │                                                          │ │
│   │   Dev  ❌     Staging  ❌     Production  ❌              │ │
│   │                                                          │ │
│   └──────────────────────────────────────────────────────────┘ │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

Multi-Cluster:
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   Dev 클러스터 장애 발생!                                      │
│   ═══════════════════════                                      │
│                    │                                            │
│                    ▼                                            │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐                    │
│   │   Dev    │  │ Staging  │  │  Prod    │                    │
│   │    ❌    │  │    ✅    │  │    ✅    │                    │
│   │          │  │          │  │          │                    │
│   │ (격리됨) │  │ (정상)   │  │ (정상)   │                    │
│   └──────────┘  └──────────┘  └──────────┘                    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 2. 업그레이드 유연성

```
단일 클러스터 업그레이드:
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   모든 환경을 동시에 업그레이드해야 함                         │
│                                                                 │
│   Day 1: 전체 클러스터 v1.30 → v1.31                          │
│                                                                 │
│   위험:                                                         │
│   • Dev 테스트 없이 Prod 업그레이드?                           │
│   • 롤백 시 모든 환경 영향                                     │
│   • 유지보수 창 조율 어려움                                    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

Multi-Cluster 업그레이드:
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   순차적, 안전한 업그레이드                                    │
│                                                                 │
│   Week 1: Dev v1.30 → v1.31                                    │
│           ├── 테스트 실행                                      │
│           └── 문제 발견 시 여기서 해결                         │
│                                                                 │
│   Week 2: Staging v1.30 → v1.31                                │
│           ├── 통합 테스트                                      │
│           └── 성능 테스트                                      │
│                                                                 │
│   Week 3: Prod v1.30 → v1.31                                   │
│           └── 검증된 절차로 안전하게                           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3. 보안 경계

```
단일 클러스터 보안:
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   모든 환경이 같은 Control Plane 공유                          │
│                                                                 │
│   위험 시나리오:                                                │
│   ├── Dev 개발자가 Prod namespace에 접근?                      │
│   ├── Dev에서 실행한 악성 컨테이너가 Prod에 영향?             │
│   └── RBAC 설정 실수로 전체 환경 노출?                        │
│                                                                 │
│   네임스페이스 격리는 완벽하지 않음:                           │
│   • 공유 리소스 (API Server, etcd)                            │
│   • 노이지 네이버 문제                                         │
│   • CVE 영향 범위                                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

Multi-Cluster 보안:
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│   환경별 완전 격리                                             │
│                                                                 │
│   ┌──────────┐  ┌──────────┐  ┌──────────┐                    │
│   │   Dev    │  │ Staging  │  │   Prod   │                    │
│   │          │  │          │  │          │                    │
│   │ 느슨한  │  │ 중간     │  │ 엄격한   │                    │
│   │ 보안    │  │ 보안     │  │ 보안     │                    │
│   └──────────┘  └──────────┘  └──────────┘                    │
│                                                                 │
│   • 클러스터별 다른 보안 정책                                  │
│   • 완전한 네트워크 격리                                       │
│   • 독립적인 RBAC                                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4. 규모 한계

Kubernetes 클러스터에는 물리적 한계가 있습니다:

| 항목 | 권장 한계 |
|------|----------|
| 노드 수 | 5,000개 |
| Pod 수 | 150,000개 |
| 노드당 Pod | 110개 |
| 네임스페이스 | 10,000개 |
| Service 수 | 10,000개 |

대규모 조직에서는 이 한계에 도달할 수 있습니다.

## Multi-Cluster가 적합한 시나리오

### 시나리오 1: 환경 분리 (Dev/Staging/Prod)

```yaml
# 환경별 클러스터 구성 예시

Dev Cluster:
  - 규모: 작음 (3-5 노드)
  - 업그레이드: 적극적 (최신 버전)
  - 보안: 느슨함
  - 비용: 최소화

Staging Cluster:
  - 규모: Prod의 1/3
  - 업그레이드: Prod 이전 테스트
  - 보안: Prod와 유사
  - 비용: 중간

Prod Cluster:
  - 규모: 필요에 따라
  - 업그레이드: 보수적
  - 보안: 엄격함
  - 비용: 필요한 만큼
```

## 트레이드오프

### Multi-Cluster의 비용

| 항목 | 단일 클러스터 | Multi-Cluster |
|------|--------------|---------------|
| Control Plane 비용 | 1x | Nx |
| 관리 복잡도 | 낮음 | 높음 |
| 도구 필요 | kubectl | ArgoCD, Flux 등 |
| 네트워킹 | 단순 | 클러스터 간 연결 필요 |
| 모니터링 | 단순 | 통합 대시보드 필요 |
| 학습 곡선 | 낮음 | 높음 |

### 언제 단일 클러스터로 충분한가

```
✅ 소규모 팀 (10명 이하)
✅ 단일 애플리케이션
✅ 규정 준수 요구사항 없음
✅ 단일 지역
✅ 낮은 트래픽
```

### 언제 Multi-Cluster가 필요한가

```
✅ 환경 분리 필요 (Dev/Staging/Prod)
✅ 다중 팀, 다중 테넌트
✅ 규정 준수 (데이터 지역성)
✅ 고가용성 요구
✅ 대규모 (노드 100+ 예상)
✅ 독립적인 업그레이드 필요
```
