# 보안

> "Kubernetes 보안은 어디서부터 시작해야 하나요?"

## 보안, 어디서부터 손대야 할까요?

Kubernetes 보안을 처음 검색하면 낯선 용어들이 쏟아집니다. 각각이 무엇인지 파악하기도 전에 "다 설정해야 한다"는 압박감이 밀려옵니다.

하지만 이 용어들은 사실 우리가 이미 알고 있는 질문들에 대한 답입니다:

| 익숙한 질문 | Kubernetes 용어 | 한 줄 설명 |
|-----------|----------------|-----------|
| "누가 이 서버에 접근할 수 있어?" | **RBAC** | 사용자별로 "무엇을 할 수 있는지" 정의 |
| "이 앱이 저 앱한테 요청해도 돼?" | **Network Policy** | Pod 간 통신 허용/차단 규칙 |
| "컨테이너가 관리자 권한으로 실행되면 위험하지 않아?" | **Pod Security Standards** | 위험한 컨테이너 설정 차단 |
| "비밀번호를 어디에 저장해야 안전해?" | **Secret 암호화** | 민감 정보 안전하게 보관 |

**좋은 소식이 있습니다.** 이 모든 것을 한 번에 설정할 필요가 없습니다.

## 실제로 사고는 어디서 발생할까요?

온프레미스 EKS 환경에서 보안 사고가 발생하면, 원인은 대부분 두 가지로 좁혀집니다.

**사례 1: 권한이 너무 넓게 열려 있었다**

한 스타트업에서 신입 개발자가 로컬 테스트 중 실수로 프로덕션 클러스터에 연결된 상태에서 `kubectl delete namespace production`을 실행했습니다. RBAC 설정이 없었기 때문에 모든 개발자가 모든 namespace에 대한 전체 권한을 가지고 있었고, 복구에 4시간이 걸렸습니다.

RBAC이 설정되어 있었다면? 신입 개발자 계정은 `development` namespace에서만 작업할 수 있었을 것이고, 프로덕션 삭제 명령은 "권한 없음" 오류로 거부되었을 것입니다.

**사례 2: Pod 간 통신이 완전히 열려 있었다**

프론트엔드 서버의 로그 라이브러리에서 취약점이 발견되었습니다. 공격자는 이 취약점을 통해 프론트엔드 Pod에 침입한 후, 내부 네트워크를 스캔했습니다. 모든 Pod가 서로 통신 가능한 기본 설정이었기 때문에, 공격자는 데이터베이스 Pod에 직접 접근하여 데이터를 탈취했습니다.

Network Policy가 설정되어 있었다면? 프론트엔드 Pod는 백엔드 API에만 통신할 수 있었을 것이고, 데이터베이스에 대한 직접 접근은 차단되었을 것입니다.

**이 두 가지를 먼저 해결하면 대부분의 사고를 예방할 수 있습니다.**

## 5계층 모델: 어디부터 시작할지 정하기

보안 설정을 체계적으로 점검하기 위해 5개 계층으로 나누어 생각하면 도움이 됩니다. 모든 계층을 한 번에 완성할 필요는 없습니다. **1~2계층을 먼저 탄탄하게 설정**하고, 나머지는 필요에 따라 강화하세요.

| 계층 | 이 계층이 답하는 질문 | 우선순위 | 대표 기술 |
|-----|---------------------|---------|----------|
| **1. 인프라** | "서버 자체가 안전한가?" | 🔴 필수 | 노드 하드닝, API Server 보안 |
| **2. 접근 관리** | "누가 무엇을 할 수 있는가?" | 🔴 필수 | RBAC, IAM, ServiceAccount |
| **3. 네트워크** | "A가 B에게 요청해도 되는가?" | 🟡 권장 | Network Policy, Service Mesh |
| **4. 워크로드** | "이 컨테이너가 안전한가?" | 🟡 권장 | Pod Security Standards, 이미지 스캔 |
| **5. 데이터** | "민감 정보가 노출되지 않는가?" | 🟢 선택 | Secret 암호화, Vault 연동 |

> 💡 **실무 팁**: 2계층(RBAC)부터 시작하세요. 설정에 30분이면 충분하고, 효과는 즉시 나타납니다. "실수로 프로덕션 삭제" 같은 사고가 원천 차단됩니다.

## 각 계층 상세: 무엇을, 왜, 어떻게

### Layer 1: 인프라 보안

서버 자체가 뚫리면 그 위에서 돌아가는 모든 보안 설정이 무의미해집니다. 

노드(서버)에 SSH로 직접 접근하면 kubelet 설정을 변경하거나, 컨테이너를 직접 조작할 수 있습니다. API Server에 아무나 접근할 수 있다면, 클러스터 전체를 장악당할 수 있습니다.

**무엇을 설정하나요?**

**노드 하드닝**은 서버에 꼭 필요한 것만 설치하고, 불필요한 접근을 막는 것입니다. Bottlerocket처럼 컨테이너 실행에 특화된 최소 OS를 사용하면 공격 표면이 줄어듭니다. SSH 접근은 긴급 상황에만 허용하고, 평소에는 차단합니다.

**API Server 보안**은 Kubernetes의 "정문"을 잠그는 것입니다. 인증 없이는 아무것도 할 수 없게 하고, 모든 요청을 감사 로그에 기록합니다.

**etcd 암호화**는 Kubernetes의 모든 상태가 저장되는 데이터베이스를 보호하는 것입니다. Secret 값도 etcd에 저장되므로, 암호화하지 않으면 etcd 백업 파일에서 비밀번호가 그대로 노출됩니다.

### Layer 2: 신원 및 접근 관리

"누가 무엇을 할 수 있는가"를 정의합니다. 이게 없으면 kubectl 접근 권한이 있는 모든 사람이 모든 것을 할 수 있습니다.

**RBAC (Role-Based Access Control)**은 "역할"을 정의하고, 사용자에게 역할을 부여하는 방식입니다.

예를 들어:
- `developer` 역할: `development` namespace에서 Pod 조회, 로그 확인 가능
- `operator` 역할: 모든 namespace에서 배포 관리 가능
- `admin` 역할: 클러스터 전체 관리 가능

신입 개발자에게는 `developer` 역할만 부여하면, 실수로 프로덕션을 삭제하는 일이 원천 차단됩니다.

**ServiceAccount**는 Pod(애플리케이션)에게 부여하는 신분증입니다. 사람이 아닌 애플리케이션도 "누구인지" 증명해야 AWS 서비스에 접근하거나 다른 Kubernetes 리소스를 조작할 수 있습니다.

**IAM 통합** (EKS Hybrid Nodes)을 사용하면 AWS IAM 사용자/역할로 Kubernetes 인증을 통합할 수 있습니다. 별도의 인증 시스템을 관리할 필요가 없어집니다.

### Layer 3: 네트워크 보안

Kubernetes의 기본 설정에서 모든 Pod는 서로 자유롭게 통신할 수 있습니다. 같은 와이파이에 연결된 기기들처럼, 네트워크 내부에서는 장벽이 없습니다.

이게 왜 문제일까요? 프론트엔드 Pod가 해킹되면, 공격자는 그 Pod에서 데이터베이스 Pod에 직접 접근할 수 있습니다. 백엔드 API를 거치지 않고요.

**Network Policy**는 "이 Pod는 저 Pod에만 통신할 수 있다"는 규칙을 정의합니다.

```yaml
# 예: 프론트엔드 Pod는 백엔드에만 통신 가능
spec:
  podSelector:
    matchLabels:
      app: frontend
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: backend
```

이 설정이 있으면, 프론트엔드 Pod에서 데이터베이스 Pod로의 직접 통신은 차단됩니다.

### Layer 4: 워크로드 보안

컨테이너가 root 권한으로 실행되면 호스트 시스템에 영향을 줄 수 있습니다. 취약점이 있는 이미지를 배포하면 알려진 공격에 노출됩니다.

**Pod Security Standards (PSS)**는 위험한 컨테이너 설정을 차단합니다. "privileged 모드 금지", "root 사용자 금지", "호스트 네트워크 접근 금지" 같은 규칙을 namespace 단위로 강제할 수 있습니다.

**이미지 스캐닝**은 컨테이너 이미지에 알려진 취약점(CVE)이 있는지 검사합니다. CI/CD 파이프라인에서 배포 전에 스캔하면, 취약한 이미지가 프로덕션에 올라가는 것을 막을 수 있습니다.

### Layer 5: 데이터 보안

API 키, 데이터베이스 비밀번호 같은 민감 정보를 어떻게 관리할 것인가의 문제입니다.

Kubernetes Secret은 기본적으로 etcd에 Base64 인코딩되어 저장됩니다. Base64는 암호화가 아닙니다. etcd 백업 파일이 노출되면 비밀번호가 그대로 드러납니다.

**Secret 암호화**를 활성화하면 etcd에 저장되기 전에 암호화됩니다. **외부 Secret 관리자** (HashiCorp Vault, AWS Secrets Manager)를 연동하면 더 강력한 보안과 자동 로테이션이 가능합니다.

## EKS Hybrid Nodes vs EKS Anywhere: 보안 책임 비교

두 솔루션은 "누가 무엇을 관리하는가"가 다릅니다.

EKS Hybrid Nodes는 Control Plane(API Server, etcd)을 AWS가 관리합니다. 인프라 보안의 상당 부분을 AWS에 맡길 수 있어 운영 부담이 줄어듭니다.

EKS Anywhere는 모든 것을 직접 관리합니다. 완전한 통제권이 있지만, 그만큼 보안 설정과 운영의 책임도 전부 지게 됩니다.

| 보안 영역 | EKS Hybrid Nodes | EKS Anywhere | 판단 기준 |
|----------|------------------|--------------|----------|
| **API Server 보안** | AWS가 관리 | 직접 설정 | 운영 역량 |
| **etcd 암호화** | 기본 제공 | 직접 설정 | 자동화 수준 |
| **인증** | IAM 통합 | OIDC 직접 구성 | 기존 IdP 활용 |
| **감사 로그** | CloudTrail 통합 | 직접 구성 | 로깅 인프라 |
| **GuardDuty** | 사용 가능 | 사용 불가 | AWS 보안 서비스 필요성 |

**어떤 것을 선택해야 할까요?**

보안 전담 인력이 부족하다면 **EKS Hybrid Nodes**가 낫습니다. Control Plane 보안을 AWS에 맡기고, 애플리케이션 레벨 보안에 집중할 수 있습니다.

규제 요건으로 모든 데이터가 온프레미스에 있어야 하거나, Control Plane까지 직접 통제해야 한다면 **EKS Anywhere**를 선택하세요.
