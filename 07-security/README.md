# 보안

> "Kubernetes 보안은 어디서부터 시작해야 하나요?"

## 보안, 어디서부터 손대야 할까요?

Kubernetes 보안은 처음 마주하면 압도적입니다. RBAC, Network Policy, Pod Security Standards, Secret 암호화... 검색할수록 설정해야 할 것만 늘어납니다.

**좋은 소식이 있습니다.** 모든 것을 한 번에 할 필요는 없습니다.

온프레미스 환경에서 EKS를 운영할 때, 실제 보안 사고의 대부분은 두 가지 원인에서 비롯됩니다:

1. **과도한 권한** — 개발자 계정이 모든 namespace에 접근 가능하거나, 실수로 프로덕션 리소스를 삭제
2. **열린 네트워크** — Pod 간 통신이 기본적으로 모두 허용되어, 하나의 Pod가 침해되면 전체로 확산

이 두 가지만 먼저 해결해도 대부분의 위험을 차단할 수 있습니다. 나머지는 상황에 따라 점진적으로 강화하면 됩니다.

## 5계층 모델로 전체 그림 이해하기

보안 설정을 체계적으로 점검하기 위해, 이 가이드에서는 5개 계층으로 나누어 설명합니다. **1~2계층은 필수**로 설정해야 하며, 3~5계층은 환경과 요구사항에 따라 선택적으로 적용합니다.

| 계층 | 핵심 질문 | 우선순위 | 주요 기술 |
|-----|---------|---------|----------|
| **1. 인프라** | "기반 시스템이 안전한가?" | 🔴 필수 | 노드 하드닝, API Server, etcd |
| **2. 접근 관리** | "누가 무엇을 할 수 있는가?" | 🔴 필수 | RBAC, IAM, ServiceAccount |
| **3. 네트워크** | "Pod가 서로 통신해야 하는가?" | 🟡 권장 | Network Policy, Service Mesh |
| **4. 워크로드** | "컨테이너가 root로 실행되어야 하는가?" | 🟡 권장 | PSS, 이미지 스캐닝 |
| **5. 데이터** | "Secret이 안전하게 관리되는가?" | 🟢 선택 | Secret 암호화, 백업 |

> 💡 **실무 팁**: 2계층(RBAC)부터 시작하세요. 대부분의 팀이 여기서 가장 큰 개선 효과를 경험합니다. 잘못된 권한으로 인한 실수와 사고를 즉시 줄일 수 있습니다.

## 각 계층이 해결하는 문제

### Layer 1: 인프라 보안 — "기초 공사"

아무리 좋은 보안 정책을 세워도, 기반 인프라가 취약하면 무의미합니다. 인프라 보안은 건물의 기초와 같습니다.

**이런 문제를 방지합니다:**
- SSH로 노드에 접근한 공격자가 클러스터 전체를 장악
- API Server에 누구나 접근 가능한 상태
- etcd 데이터가 평문으로 저장되어 민감 정보 노출

**핵심 설정:**
- **노드 하드닝**: 최소한의 OS만 설치(Bottlerocket 권장), SSH 접근 제한, CIS 벤치마크 적용
- **API Server**: 인증 필수화, 감사 로깅 활성화, 익명 접근 차단
- **etcd**: 저장 시 암호화(encryption at rest), TLS 통신, 접근 제한

### Layer 2: 신원 및 접근 관리 — "누가 무엇을 할 수 있는가"

Kubernetes에서 가장 흔한 보안 사고는 "권한 관리 미흡"입니다. 개발자가 실수로 프로덕션 Pod를 삭제하거나, 테스트용 계정이 민감한 Secret에 접근하는 상황을 막아야 합니다.

**이런 문제를 방지합니다:**
- 인턴 계정으로 프로덕션 배포 삭제
- 모든 개발자가 모든 namespace의 Secret 조회 가능
- 서비스 계정이 필요 이상의 권한 보유

**핵심 설정:**
- **RBAC**: 역할 기반으로 최소 권한만 부여 (least privilege principle)
- **ServiceAccount**: Pod별로 필요한 권한만 가진 전용 계정 사용
- **IAM 통합**: EKS Hybrid Nodes에서는 AWS IAM으로 일관된 인증/인가 구현

### Layer 3: 네트워크 보안 — "Pod 간 통신 통제"

Kubernetes의 기본 네트워크 정책은 "모든 Pod가 서로 통신 가능"입니다. 이는 편리하지만, 하나의 Pod가 침해되면 클러스터 전체로 공격이 확산될 수 있습니다.

**이런 문제를 방지합니다:**
- 프론트엔드 Pod에서 데이터베이스 Pod에 직접 접근
- 한 팀의 서비스가 다른 팀의 내부 API 호출
- 침해된 Pod가 다른 모든 Pod를 스캔

**핵심 설정:**
- **Network Policy**: Pod 간 허용할 트래픽만 명시적으로 정의
- **Service Mesh**: mTLS로 Pod 간 통신 암호화, 세밀한 트래픽 제어
- **방화벽**: 클러스터 경계에서 외부 접근 통제

### Layer 4: 워크로드 보안 — "컨테이너 자체의 안전"

컨테이너가 root 권한으로 실행되거나, 취약한 이미지를 사용하면 클러스터 전체가 위험해집니다.

**이런 문제를 방지합니다:**
- root 권한 컨테이너가 호스트 파일시스템 접근
- 알려진 취약점이 있는 이미지 배포
- 런타임에 악성 프로세스 실행

**핵심 설정:**
- **Pod Security Standards**: 위험한 설정(privileged, hostNetwork 등) 차단
- **이미지 스캐닝**: 배포 전 취약점 검사
- **런타임 보안**: 이상 행위 탐지 및 차단

### Layer 5: 데이터 보안 — "민감 데이터 보호"

API 키, 데이터베이스 비밀번호 등 민감한 데이터가 안전하게 관리되어야 합니다.

**이런 문제를 방지합니다:**
- Secret이 etcd에 평문으로 저장
- 백업 파일에서 민감 정보 노출
- Secret이 로그에 출력

**핵심 설정:**
- **Secret 관리**: 외부 시크릿 관리자(Vault, AWS Secrets Manager) 연동
- **암호화**: 전송 중(in transit), 저장 시(at rest) 모두 암호화
- **백업**: 재해 복구를 위한 안전한 백업 전략

## EKS Hybrid Nodes vs EKS Anywhere: 보안 책임 비교

두 솔루션은 보안 관리 책임이 크게 다릅니다. EKS Hybrid Nodes는 AWS가 Control Plane 보안을 담당하므로 운영 부담이 적고, EKS Anywhere는 완전한 통제권을 얻는 대신 모든 보안을 직접 관리해야 합니다.

| 보안 영역 | EKS Hybrid Nodes | EKS Anywhere | 선택 기준 |
|----------|------------------|--------------|----------|
| **API Server** | AWS 관리 ✅ | 직접 관리 | Control Plane 운영 역량 |
| **etcd 암호화** | AWS 관리 ✅ | 직접 구성 | 보안 설정 자동화 수준 |
| **인증** | IAM 통합 ✅ | OIDC 직접 구성 | 기존 IdP 활용 필요성 |
| **감사 로그** | CloudTrail ✅ | 직접 구성 | 로깅 인프라 보유 여부 |
| **노드 보안** | 직접 관리 | 직접 관리 | 동일 |
| **네트워크 보안** | 직접 관리 | 직접 관리 | 동일 |
| **GuardDuty** | 지원 ✅ | 미지원 ❌ | AWS 보안 서비스 필요성 |

> 🎯 **결론**: 보안 운영 역량이 제한적이라면 **EKS Hybrid Nodes**를, 규제 요건으로 완전한 통제가 필요하다면 **EKS Anywhere**를 선택하세요.
